## q30 — Quantization explained

**Q:** Explain what 4-bit quantization does to an LLM and when it actually matters. Keep it short and technical.

*41.69s, 2869 chars, models: Ollama1 · gpt-oss:20b, Ollama1 · ministral-3:14b, Ollama1 · gemma4:12b, searched: False, drafts: Ollama1 · gpt-oss:20b, Ollama1 · gemma4:12b, Ollama1 · ministral-3:14b (review)*

4‑bit quantization compresses every 32‑bit weight into a **4‑bit signed integer** (16 discrete levels), shrinking the weight tensor to **1/8** the size of FP32 and to **1/4** of FP16.

The usual mapping is  

\[
w_{\text{q}}=\operatorname{round}\!\left(\frac{w-\min}{\max-\min}\times15\right)-8,
\]

where *min* and *max* are per‑layer calibration values.  
Most production pipelines use **weight‑only** quantization because it keeps the runtime hardware simple, but activations can be quantized in the same way if the accelerator supports int4 math.

### What the math does to the model

* **Dynamic‑range sensitivity** – If a layer contains a few extreme outliers, the linear map can push many useful weights into a single quantization bin, increasing error. Per‑layer scaling and zero‑point calibration mitigate this but cannot fully eliminate it.  
* **Attention mechanics** – The soft‑max in self‑attention uses the dot‑product of quantized queries and keys. While int4 dot‑products are fine for forward passes, the resulting logits can be noisier, slightly degrading probability calibration. In practice, the impact on perplexity is usually below 1 % when the scaling is tuned.  
* **Gradient flow** – During fine‑tuning, the weights stay in int4, but gradients are still accumulated in float32 (or float16). If you enable gradient checkpointing, the reduced precision can break accumulation in the backward pass; most frameworks therefore keep the checkpointed activations in higher precision or disable checkpointing for int4 models.

### When 4‑bit matters

| Scenario | Benefit | Caveat |
|----------|---------|--------|
| **Memory‑constrained inference** (e.g., a 7 B model on an 8 GB GPU) | **8×** memory savings lets you fit the model or run larger batches. | Requires careful calibration; typical accuracy loss is **2–4 %** on generation benchmarks. |
| **Edge or mobile deployment** | Enables on‑device inference with minimal model download and fast warm‑start. | Hardware must support int4 ops; otherwise you need extra CPU de‑quantization, which can offset the speed gain. |
| **Cost‑sensitive cloud inference** | Reduces storage and bandwidth, sometimes allowing cheaper GPU or CPU instances. | The same accuracy trade‑off applies; validate against your SLA. |
| **Fine‑tuning or LoRA updates** | QLoRA keeps weights at int4 while gradients stay high‑precision, allowing training on modest GPUs. | Requires a quantization‑aware training pipeline; gradient checkpointing can break with 4‑bit, so either avoid it or use float‑32 checkpoints. |

### Bottom line

If you must squeeze a large LLM into limited memory or run it on low‑power hardware, 4‑bit quantization is the go‑to choice. For cloud inference where top‑level accuracy is critical, stay with **8‑bit** or **FP16** unless you’ve validated that the 2–4 % drop is acceptable for your workload.
